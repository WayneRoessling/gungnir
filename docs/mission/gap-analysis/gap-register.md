**GAP-001 Live sensor adapters**

- Type: Technical.
- Capability: CAP-1.1 Ingest observations.
- Description: **The acoustic and passive-RF adapters are built and gated 2026-09-07, the second item of this gap's own closing action, and this crate is human-owned: signed by the owner 2026-09-08.** `gungnir-ingest/src/adapters/sapient.rs` accepted only `NODE_TYPE_HUMAN` until now, refusing `NODE_TYPE_ACOUSTIC` and `NODE_TYPE_PASSIVE_RF` by name (`another_node_type_is_named_rather_than_accepted`). Reading the mapping code that refusal guarded -- `map`, `range_bearing`, `location`, `source_time` -- found nothing that assumes a human observer: no default accuracy, no instrument-specific unit, no error model invented where the report states none, exactly as the register already said when it called these three feeds 'the same message set and the same adapter shape.' The registration gate was the whole of the restriction, not the measurement mapping underneath it. `SpotterAdapter` is renamed `SapientDetectionAdapter` (confirmed unreferenced outside this crate before the rename, so the blast radius is this module and its own tests), takes the one node type it accepts as a constructor argument rather than a hardcoded constant, and a mismatched registration is still refused and named -- now provably in both directions (`an_instance_built_for_one_node_type_refuses_a_different_one`), not only the human-accepts/acoustic-refused case the original test held. Two new tests drive an acoustic array's bearing and a passive-RF node's ranged report through the real mapping code and confirm each becomes exactly what a spotter's identical report would; a fifth test loops the three named types together against the constant that documents them, so a fourth type added to one and not the other fails a test rather than shipping silently out of step. 15 tests in the module, all passing (was 11; four new: the reverse-direction refusal, the acoustic bearing, the passive-RF ranged report, and the loop over all three named types). **Wired 2026-09-07, the same day.** `ConfigBaseline.sapient_feeds` names each feed's sensor (siting and identity, the same lookup `radar.rs` makes for a radar), its node type, and a `Tcp{addr}`/`File{path}` source, validated the same way `ais_feeds` and the new `adsb_feeds` are (once per name, a sensor that exists, one feed per sensor, a source that parses). `TcpSapientSource` moved into this module from a first draft that had it duplicated per binary, so both `gungnir-app/src/sapient.rs` and `gungnir-node/src/main.rs` share the one implementation, exactly as `ais::TcpNmeaSource` and `adsb::TcpAvrSource` already do. **Unlike AIS and ADS-B this is not a cooperative-identity feed**: a SAPIENT node reports a detection of something else, not a claim about itself, so its output is a `DetectionView` into the gateway like a radar's, and there is no per-frame tick, no association, and no evidence-fusion edge to be missing on the node -- `gungnir-app/src/sapient.rs`'s own module documentation says this in full. Both binaries bind every configured feed at start; a deployment with no local frame origin binds nothing and says why, matching every other feed type. **The sensor-position resolver is built and wired 2026-09-07, which is the first item of this gap's own closing action.** `DetectionView` carries a `SensorId` and not a position, deliberately -- a detection says who saw something, and where that sensor is belongs to the deployment -- and **nothing joined the two**, so `LiveTrackingService` refused every angular measurement with `NotAPosition`. Three of the six feed types this gap lists report angles, so the refusal was the wall in front of acoustic, passive-RF and spotter feeds. `gungnir_tracking_service::SensorPositions` is that join, built from the baseline's own sensor list and handed in as data (this crate may not depend on `gungnir-config`), and **both binaries now supply it** rather than it being a type with no caller. What it permits and what it still forbids: a **range, azimuth and elevation** report is now placed from the reporting sensor and reaches the pipeline, which is arithmetic and not assumption -- a range from a known point *is* a position, and DN-27 §2's prohibition does not reach it. A **bearing** reaches the tracker as a bearing, through a new `gungnir_fusion_async::Submission` enum whose two variants route to `push` and `offer_bearing` respectively, so DN-27 §5's rules apply and are enforced by the type rather than by a check: it may refine a track, it may not initiate one, and if it matches nothing it is retained and shown. **Two refusals are kept and distinguished**: no resolver at all is `NotAPosition`, and a sensor the baseline never declared is `UnknownSensorPosition(id)` -- collapsing them would send an operator hunting for missing wiring when the answer is a missing line in a baseline. There is no origin fallback anywhere: placing a bearing from [0,0,0] because the sensor is unknown would draw a ray from the wrong place with nothing indicating an assumption. `gungnir-tracking-service/tests/sensor_position_resolver.rs`, eight tests, of which the negative ones are the point. **A limitation recorded rather than hidden**: the stated variance of a range-azimuth-elevation report does not survive the conversion, because `gungnir_fusion_async::Detection` carries a position and no error and the pipeline gates on its settings; carrying it properly needs the Jacobian of the transform and a field to put it in, which is the same missing field DN-27 §6 describes. The bearing path does not have the problem: `BearingDetection` carries its angular variance and the pipeline uses it. **Human-owned and unsigned**: the change touches `gungnir-fusion-async`. **Signed by the owner 2026-09-06**: the SAPIENT spotter adapter in the `gungnir-ingest` gateway, which the low-trust list names as the trust boundary for external data. **DN-27, the design behind it, was not in that signature at the time and is signed by the owner as of 2026-09-07.** **The spotter half is BUILT and gated 2026-09-06**, on the owner's recommended order: the design note first, then the pin, then the feed that needs no hardware. DN-27 is written and signed by the owner (2026-09-07); SAPIENT ICD v7 is pinned under the Open Government Licence with its Apache-2.0 schemas and sample messages, and the fixtures are vendored under `testdata/sapient/`. `gungnir_ingest::adapters::sapient` accepts `NODE_TYPE_HUMAN` registrations and maps a bearing to `Measurement::Bearing`, a lased range to `RangeAzimuthElevation`, and a Cartesian location to `Position`; everything it does not handle is counted **and named**. **The acoustic and passive-RF halves are the same message set and the same adapter shape**, so what remains for them is configuration and taxonomy rather than a new build. ISR video stays deferred: it is a video transport carrying metadata rather than a detection message, and belongs with the viewport work. **Corrected 2026-09-06: 'blocked on interface agreements nobody has' was wrong, for all four feeds.** A survey the same day found a free, publicly downloadable specification for every one of them, and for three of them the same one. **SAPIENT** -- the UK Dstl sensor-network interface, adopted by NATO as STANREC 4869 with STANAG ratification in progress -- names acoustic (`NODE_TYPE_ACOUSTIC`), passive RF (`NODE_TYPE_PASSIVE_RF`) and a person (`NODE_TYPE_HUMAN`) as node types in one interface control document. **The ICD v7 is Open Government Licence v3.0 and therefore redistributable**; its protobuf schemas and its sample messages are Apache-2.0. So the rule GAP-064 set -- a pinned specification and a public sample in the repository -- is satisfiable for three feeds **without a single agreement**. (Note the licence split: BSI Flex 335, the current *normative* version, is free to read and **not** redistributable, so the OGL ICD is what may be vendored.) **ISR video** is the MISB family, free and unauthenticated from the NSG Standards Registry -- ST 0601.19, ST 0102.12, ST 1402.2, ST 0807.27, profiled by MISP-2025.1 -- and STANAG 4609 Edition 5 itself is public and NON CLASSIFIED. Its residual gap is a **fixture**, not a specification: the widely used FFmpeg sample files state no licence at all and must not be vendored, while `paretech/klvdata` ships a small MIT KLV binary that may be. **Radio direction finding** is cheapest of all: **ASTERIX Category 205**, Edition 1.0, marked 'Released Issue, intended for General Public' on its own status page, in the document family this workspace already pins. **The real work is not procurement, it is one design decision.** A bearing-only detection is not a position, and `DetectionView` carries a position. Inventing a range to make one fit would be exactly the confidently-wrong answer this system forbids. That wants a design note before any of the three adapters is written. The one thing that does cost money is drone Remote ID -- ASTM F3411 and ASD-STAN prEN 4709-002 are paid, of the order of seventy dollars -- and that is a standards fee, not an interface agreement. NATO ACCS ASTERIX categories 158 and 160 are on topic and are not public. Full survey in `../../design/external-standards.md` §§7 to 9. **Examined 2026-09-06: what remains is blocked on documents, not on engineering.** The radar half is built and gated on a public capture, and the ASTERIX editions it was written against are pinned in `../../design/external-standards.md`. The four remaining feeds -- acoustic, RF, ISR video and spotter -- have **no pinned format anywhere in this repository**: `external-standards.md` covers ASTERIX and AIS and nothing else, so there is no edition to write a decoder against and no capture to gate it on. Writing one from a guessed wire format would produce a decoder that compiles, passes its own tests, and has never seen the sensor it claims to read. **The blocker is procurement of an interface agreement per feed, and that is not a coding task.** **The node reports its feeds 2026-09-06** (step 5): every radar feed's counters and every peer link's state on the health line, since the node has no panel. The service-report queue had its consumer since GAP-064. **The feeds report themselves 2026-09-06.** `AsterixFeedAdapter` publishes its counters at the end of every poll (`FeedStatsSink`, beside the service-observation sink in `FeedSinks`), and PN-09 draws a line per bound feed: datagrams, detections, service reports, what did not decode, and what came from a radar no binding names. A feed bound and hearing nothing is said in the warning colour rather than passing for health; the node keeps the same sink and has no panel to draw it on. **The radar half is wired 2026-09-06** (handoff §4 steps 1 and 2): `ConfigBaseline.radar_feeds` names a socket, an optional multicast group, and the SAC/SIC pairs bound to sensors, validated so an unknown sensor, a duplicate pair, or an unparseable address fails rather than defaults; both hosts bind a `UdpDatagramSource` per feed, build the adapter with the sensors' positions in the local frame, and register it with the gateway -- and a deployment with no origin binds nothing and says why. The service-report queue now has a consumer (GAP-064). EO/IR, acoustic, RF, ISR video and spotter feeds still have no adapter; `AsterixFeedStats` is still unpublished (step 5). Real radar, EO/IR, acoustic, RF, ISR video, and spotter-application feeds need adapters behind the `gungnir-ingest` gateway. **The radar half landed 2026-09-06** (built in a parallel session; the register reconciled from the code the same day): `gungnir-ingest/src/adapters/asterix.rs` splits each datagram into data blocks, routes Category 048 target reports through the codec to the gateway as `DetectionView`s and Category 034 service messages into the adapter's own queue -- the `ProtocolAdapter` boundary carries detections only, and a service message is not one -- and counts rather than hides a datagram that does not frame, a block that does not decode, a report from a radar the baseline does not name, and a category the build does not speak (`AsterixFeedStats`). Gated on the public capture under `testdata/asterix/` (provenance in its `SOURCE.md`), on `gungnir-ingest/tests/asterix_feed.rs` end to end through the gateway to a tracking service, and on the `asterix_feed` fuzz target with its seed corpus. This added edge (j) `gungnir-ingest` to `gungnir-interop`, described by `../../../ARCHITECTURE.md` §8.6 from the first draft and carried by no manifest until an adapter existed. **Still open**: EO/IR, acoustic, RF, ISR video and spotter feeds have no adapter; nothing consumes the service-report queue yet; no live transport is bound to the adapter in either binary.

**GAP-024 Point-cloud registration, CPU reference and GPU**

- Type: Technical.

- Description: **The point-to-plane CPU reference is built 2026-09-08, the half of this gap's own closing action that did not need the GPU runner.** `gungnir-data-fusion::point_to_plane::point_to_plane_transform` is the linearised normal-equations solve: a small rotation `R = I + [ω]×` and translation `t` minimising the summed squared point-to-plane distance is linear in six unknowns via the scalar triple product identity `n·(ω×p) = ω·(p×n)`, giving `A x = b` with `A` the 6x6 sum of outer products `[p×n; n][p×n; n]ᵀ`; the solved rotation vector is turned back into a rotation via `UnitQuaternion::from_scaled_axis` (the true exponential map) rather than the non-orthogonal `I + [ω]×` the linearisation itself used. `CpuIcpPointToPlane` drives it the same way `CpuIcp` drives Kabsch --  correspond by nearest point, solve, compose, judge convergence -- refusing at construction when `target.normals` is `None` rather than estimating one itself. **A degeneracy check earns its place rather than being assumed**: `A`'s smallest-to-largest eigenvalue ratio below `1e-6` (`normals.rs`'s own collinearity threshold, same shape of problem) is refused as `Degenerate`, catching the planar-or-near-planar case where every normal points the same way and no combination of points can tell a rotation about it from a translation within it. **That case was not hypothetical**: `cpu_reference.rs`'s and `normals.rs`'s own shared test surface (`z = sin(1.3x+0.7y)*0.4`) turned out to be exactly this kind of degenerate for the point-to-plane solve specifically -- `cond(A)` came out above `10^17` in the independent Python check below, though the same surface is perfectly fine for `estimate_normals`'s own per-point PCA, which never sums curvature information globally the way this solve does.
