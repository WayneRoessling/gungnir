# §10 item 133

Filed under `ARCHITECTURE.md` §10's "Resolved on 2026-09-15" heading, and moved here on
2026-09-16 with its wording unchanged.

**Gate 6 moved onto the self-hosted runner, 2026-09-15, and enforcement deliberately
left behind (GAP-093).** `bench-regression.yml` ran on `ubuntu-latest` while its own
header said the thing standing between it and a failing threshold was "a runner, not a
threshold": the evidence it records is a run where every benchmark came out between
0.49x and 0.91x, which is the signature of a different machine and not of a change. The
job now runs on `gungnir-rtx-5060ti`, the one self-hosted runner this repository has.

**It was not the one-line change it was described as**, and the difference is worth
recording because the same shape will recur for any job that moves to this runner.
Three things came with the move. The runner is **Windows**, so both `run:` steps need
`shell: bash` -- a PowerShell default meets `if [ "$GITHUB_REF" = ... ]` and a
`<<'PY'` heredoc as syntax errors. The labels pin a **machine** rather than a
capability: `gpu` is in the list because it is what identifies this host, no benchmark
here touches a GPU, and a second self-hosted runner would make
`[self-hosted, Windows, X64]` match either box and silently restore the cross-machine
comparison the move exists to end -- so the workflow says to give it a `bench` label
of its own on that day. And a self-hosted runner **keeps its working directory between
runs**, which a hosted one cannot: `actions/cache/restore` merges into whatever is
already there, so a `target/criterion` left by an earlier run, another branch, or
somebody's local `cargo bench` on this workstation would be read as the baseline with
nothing saying so. A clearing step ahead of the restore makes the restore
authoritative again. That hazard is created by the move; on `ubuntu-latest` the
directory could only ever hold what the restore put there.

**Enforcement stays off, and same-machine turned out to be necessary rather than
sufficient.** Two things stand between the move and `BENCH_REGRESSION_ENFORCE: "1"`.
Every saved baseline was written by a hosted runner, so comparing against one would be
the cross-machine comparison this move ends; the first push to main after it writes a
fresh one. And **this machine has a specific reason for a wide noise floor**: it is an
8 P-core / 12 E-core hybrid, and a benchmark scheduled onto an efficiency core runs
about twice as slow as the same benchmark on a performance core. That is a 2x swing
with no code change against a 10 percent threshold -- the same unattributable
difference that took enforcement off the hosted runners, reproduced on one machine in
a smaller package. The measurement that settles it is two dispatches with no code
change between them: within a few percent and the threshold is enforceable; a whole
set moving together is the core class, and enforcement then needs affinity pinning or
criterion's statistical comparison in place of a raw mean ratio. The `pull_request`
trigger returns with enforcement and not before, which is what the header already
said.

**Nothing in the repository's code changed**, and the gate's exit status is unchanged:
it still prints every ratio and every threshold breach and still refuses to fail on a
number it cannot attribute. What changed is where the numbers come from.
