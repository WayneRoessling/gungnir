# Verification Capability Table

Cross-tool verification matrix: Rust modules, target capabilities, Python/MATLAB oracles, verification method, pass criteria, and data source. Companion reference to `scenario-crate-narrative.md` (why the scenario-generated rows are covered by five scenarios), `architecture.md` (which crate owns each module), and `gungnir-capabilities.md` (the business reading of each row).

§1 is the tracking core's matrix and is the source of truth for every pass criterion the crate doc comments restate. §2 is a draft for the other layers: the verification method is taken from the design documents, and every pass criterion that had no value was set by the owner on 2026-09-04 (D-16); the rows stay Draft until their tests exist. Row names in §1 are cited from Rust doc comments and must not be changed.

Five limits are recorded rather than papered over.

- **MATLAB is not installed on the development machine.** The `initcvkf`, `initcakf`, and `initctekf` column of the motion-model row was not run. The row is gated on its Python and scipy columns alone; nothing in `testdata/oracles/` is a MATLAB result, and `testdata/oracles/README.md` says so. Every other row whose only oracle is MATLAB stays Draft.
- **`purity` is not a `motmetrics` metric.** `motmetrics` publishes none, so the fixture computes purity from `motmetrics`' own event dataframe by the definition `gungnir-metrics` documents. MOTA, MOTP and fragmentation are the oracle's own outputs; purity is a check of the aggregation given an agreed matching, and the matching is what those three already pin. Worth having, but not the same claim, and both the fixture and the test say so.
- **Only half the lifecycle oracle is driven end to end.** Stone Soup's `UpdateTimeStepsDeleter` is a real object driven against a real `Track`, so the deletion step index is its own answer. The confirmation step index is the condition lifted verbatim from `MultiMeasurementInitiator.initiate` and evaluated against that same `Track`, because running the whole initiator would interpose a predictor, updater, associator and measurement model between the fixture and the one rule under test. Both the fixture and the Rust test say which is which.
- **An assignment problem can have several optima of equal cost**, and which one a solver returns is an artifact of its pivoting order, which is why the Hungarian row says "assignment only if not tied". The fixture decides uniqueness by brute force over all permutations rather than assuming it, and records the answer per case; the pairing is compared only where the optimum is provably unique (11 of 15 cases), and the cost is compared everywhere. "Exact" on the cost means to the rounding of a sum taken in a different order than the oracle takes it, which is 1.9e-16 relative in practice.
- **Stone Soup's `KnownTurnRate` divides by the turn rate.** It returns NaN at `omega == 0` and loses most of its significant digits as the turn rate approaches zero. Those cases are listed in the fixture's `degenerate_oracles` and the Stone Soup column is dropped for them, with scipy's `expm` adjudicating instead. This is a limitation of the reference, not of the model: `gungnir-core` evaluates the same terms through a small-angle series precisely so that it is not.

The oracle fixtures are checked in under `../testdata/oracles/`, with the generators that produce them and the oracle versions they were produced from, so the differential tests run on a machine with no Python installed.

## Notes

- **Real dataset placement was deliberate.** Real flight data (ADS-B/OpenSky) is scoped to the IMM and RTS-smoother rows only, not the base `core` CV/CA/CT row — that row's pass criterion is an exact-match closed-form check, and real noisy trajectories don't add anything over a synthetic fixture there. No other real trajectory source is currently assigned to a row.
- **Stone Soup example scenarios** are added to JPDA, PHD/CPHD, and GLMB/LMB specifically, where Stone Soup is already the named oracle — same library as source and oracle, less risk of mismatch.
- **DARPA/ONR/Vo et al. companion data** is scoped to "where available," contingent on which specific GM-PHD/GLMB paper is being implemented against.
- **MOT20** (crowd-scene, denser than MOT16/17) is a candidate real-data complement to the dense-swarm synthetic scenario, if a real-data stress case is wanted alongside the synthetic one — not yet formally assigned to a row.

capabilities. Each was written before any of its code exists, so its criterion could not be
fitted to an implementation (AP-17), and the owner agreed them all on 2026-09-05.

Like every other row in this section they are **not gates yet**: a row becomes a gate when
its test lands and its status moves in `architecture.md`, under GAP-067. The design note
each row came from is `design/verification-rows.md`, which maps row to note to crate.

**One row cannot be gated by any build, and it is worth saying why (2026-09-05).**
`gungnir-workflow` / Collection requirements and tasking concurrence (CAP-2.12) is built
and exercised by `gungnir-app/tests/requirements.rs` -- a requirement is answered only
with evidence, a lapse is distinguished from a decline, and a requirement moves to tasked
only when a task exists. But its criterion asks for a concurrence **carrying an
operator**, and no build has an operator session (GAP-057): every concurrence this system
can produce records a role and states that nobody was signed in. The criterion is left
exactly as agreed rather than widened to accept a role, and `gungnir_model::Concurrence`
is shaped so that `operator()` is the predicate the row will be checked against once
GAP-057 lands. Its method is also an MT-08 replay, which needs the TT-08 integration
(GAP-076).

**One of them now has its test (2026-09-05).** `gungnir-sensor-management` / Outbound
sensor control and acknowledgement (CAP-1.3) is exercised by `mod tests` in
`gungnir-sensor-management/src/lib.rs` against a `StubAdapter` that accepts, refuses, or
ignores, and end to end through the desktop tick in `gungnir-app/tests/sensor_control.rs`.
The criterion was not touched: the `SensorControlAdapter` seam was built so that the
method this row already named -- a stub adapter -- is the method actually used, rather
than the row being reworded to match tests that called the registry directly. It stays
listed as not-a-gate until GAP-067 moves its status, which is that gap's job and not this
change's.
